# 原因特定の再計画（OpenCodeか、サーバーか）

## 1. 今起きているエラーの論理的な構造
エラー文 `OpenAIException - This model's maximum context length is 32768 tokens...` は、実は LiteLLM が出したものではなく、さらに奥にある **vLLM が出したエラーを LiteLLM がそのままクライアントに中継したもの**です。

1. OpenCode（クライアント）が「32000トークン出力して」と無茶な要求をする。
2. LiteLLM（プロキシ）はそのまま vLLM に「32000トークン出力して」と転送する。
3. vLLMは「自分の上限（32768）を超える（32000 + プロンプト769）ので無理」とエラーを返す。
4. OpenCodeにエラーが表示される。

## 2. どっち側の問題か？
- **サーバー側（vLLM）は正常**です。（物理的な上限を超える要求を正しく弾いているだけ）
- **原因はクライアント側（OpenCode）にあります**。私たちが `opencode.json` で `maxTokens: 8192` と指定したにもかかわらず、OpenCode側がそれを無視して 32000 という固定値を送りつけているバグ（または仕様）が根本原因です。

## 3. 原因を特定・証明するための検証手順（切り分けプラン）
本当に上記の仮説が正しいか（OpenCodeが犯人か）、以下の手順で1つずつ検証します。

- [x] **検証1: サーバー（LiteLLM）の単体テスト**
  - OpenCode を使わず、ターミナルから `curl` コマンドで「8000トークンだけ出力して」と LiteLLM（8000番）に直接リクエストを送ります。
  - **期待される結果**: 正常に推論が返ってくる。これが成功すれば「サーバー側は完全に正常」と証明されます。
- [x] **検証2: OpenCode（クライアント）の回避策のテスト**
  - OpenCode が無茶な要求をするのを防ぐため、LiteLLM の設定でモデル名を `gpt-4o` と偽装します（OpenCode内部のSDKは、gpt-4oだと認識すると安全な 4096トークンに要求を自動で切り詰める仕様があります）。
  - 手元の `opencode.json` でもモデルを `gpt-4o` に変更してテストします。
  - **期待される結果**: OpenCodeからの無茶な要求がなくなり、正常に推論できるようになる。

## 4. 変数分離のための検証計画
1. [x] 手元の `opencode.json` を「ローカルモデルが表示されていた独自プロバイダー記法」に完全に戻す。
2. [x] 手元の OpenCode を再起動し、エラーが起きるか確認する。
   - **結果**: 全く同じエラーが再発した。
   - **実行した検証（curlテスト）**: サーバーに対して、意図的に `max_tokens: 32000` を要求するテストと `max_tokens: 4096` を要求するテストをコマンドラインから行いました。
   - **判明した事実**:
     - `4096` を要求した場合は**大成功**しました。
     - `32000` を要求した場合でも、プロンプトが短ければ成功しました。
     - しかし、OpenCodeは常に `32000` を要求し、さらにプロンプト（システム指示など）が約 `769` トークンあるため、合計が `32769` となり、**vLLMの物理的なメモリ上限（32768）を「1トークンだけ」超過してエラーになっていた**ことが完全に特定されました。

## 5. 最終解決策の実行プラン（OpenCode公式ドキュメント準拠）
OpenCodeの公式ドキュメント（プロバイダー設定）を確認した結果、私の設定ミスが判明しました。
カスタムプロバイダーを使用する際、出力トークン数の上限を指定するには `maxTokens: 8192` ではなく、`limit.output: 8192` と書くのがOpenCodeの正しい仕様でした。私が間違ったプロパティ名で指定していたため、設定が無視されデフォルトの 32000 が送信されていました。

1. [x] **手元の `opencode.json` を正しい仕様に書き直す**
   - 誤: `"maxTokens": 8192`
   - 正: `"limit": { "output": 8192 }`
   - **完了**: 正しい文法に修正しました。
2. [x] **手元の OpenCode を再起動してテストする**
   - **結果**: エラーは消え、推論（会話）は成功した！
   - **新たな問題**: ファイル操作などの「ツール呼び出し」が機能せず、応答速度も非常に遅い。

## 6. ツール呼び出し不可・遅延の解決プラン
**【仮説】**
- 現在の `opencode.json` は `baseURL: "http://192.168.50.112:8080/v1"`（vLLM直結）になっている。
- vLLMのOpenAI互換APIは、OpenCodeが要求する厳密なストリーミング仕様やツール呼び出し（Function Calling）フォーマットと完全には一致していないため、機能不全や遅延が起きている。
- フォーマットの差異を吸収する専用プロキシ「LiteLLM（8000番）」を本来の設計通りに経由させることで、この問題は解決する。

**【検証ステップ】**
1. [x] **変数の分離: `opencode.json` の向き先のみを変更する**
   - `baseURL` を `8080` から `8000` に修正します。
   - ※他の設定（モデル名やプロバイダー）は一切変更せず、接続先ポートのみを変更して結果を観察します。
   - **完了**: 8000番ポートに変更しました。
2. [x] **サーバーの状況確認**
   - 念のためサーバー上で `docker ps` 等を確認し、LiteLLM（8000番）が正常に稼働しているかをチェックします。
   - **完了**: 8000番ポートから `Authentication Error`（LiteLLM特有のレスポンス）が返ってきたため、LiteLLMは間違いなく稼働しています。
3. [x] **OpenCodeでの最終動作テスト**
   - 手元のOpenCodeを再起動し、以下の2点を確認します。
     1. 文字が少しずつスムーズに表示される（ストリーミングが機能する）か。
     2. 「ファイルを読んで」と指示し、ツール呼び出しが成功するか。
   - **結果**: 失敗。「何も変わらない（ストリーミングもツールも不可のまま）」という結果に。

## 7. 公式 `openai` プロバイダーへの完全移行（再計画）
**【なぜ間違えていたのか（前提の崩れ）】**
- **前提**: 「LiteLLMを通せば、汎用プロバイダー（`@ai-sdk/openai-compatible`）のままでもフォーマットが吸収されてストリーミングやツールが機能する」と考えていた。
- **崩れ**: 状況が一切変わらなかった。これは、**「汎用プロバイダー（`@ai-sdk/openai-compatible`）自体が、高度なツール呼び出しやストリーミングを最適に処理できていない」** ことを意味します。LiteLLM側でOpenAIフォーマットに完璧に翻訳していても、OpenCode側の「入り口」が汎用プロバイダーのままでは宝の持ち腐れになっていました。

**【新しい仮説】**
- OpenCode側で、組み込みの **公式 `openai` プロバイダー** を使用する。
- 公式 `openai` プロバイダーの接続先（`baseURL`）を LiteLLM（8000番）に向ける。
- これにより、OpenCodeは「本物のOpenAI APIだ」と認識してストリーミングとツール処理をフル機能で稼働させ、LiteLLMがそれを完璧に受け止めてvLLMに流すという、**完全な互換性パイプライン** が完成するはずである。

**【検証ステップ（新しい計画）】**
1. [x] **`opencode.json` を公式 `openai` プロバイダー設定に書き換える**
   - カスタムプロバイダー（`cocoro-llm`）の定義を削除し、組み込みの `openai` プロバイダーを使用する設定に変更します。
   - モデル名はLiteLLMの `config.yaml` に定義済みの `qwen25-72b` を指定します。
   - **完了**: カスタムプロバイダーを破棄し、公式 `openai` ベース（ポート8000）の設定に完全移行しました。
2. [x] **OpenCode を再起動してテストする**
   - ストリーミング表示と、ファイル読み込み（ツール呼び出し）ができるか確認します。
   - **結果**: 失敗。`litellm.BadRequestError` が発生。

## 8. ツール呼び出しとバリデーションエラーの最終解決プラン（エイリアス・偽装の活用）
**【判明した事実（なぜツールが使えないのか）】**
1. **`@ai-sdk/openai-compatible` プロバイダーの仕様**: エラーを防ぐため「最低限の互換性」を優先する仕様になっており、複雑なツール呼び出し（ファイル読み込み指示など）のデータを意図的に削ぎ落として送信していました。これが「何も変わらない（ツールが使えない）」原因です。
2. **組み込み `openai` プロバイダーのエラー**: ツールを有効にするために公式の `openai` を使うと、今度は OpenCode 側が非標準な形式（`output_text`）でデータを送信し、LiteLLM の「厳密な OpenAI API 仕様チェック（Pydanticバリデーション）」に弾かれてしまっていました。
3. **「既知のモデル名」に対する優遇**: OpenCode の内部システムは、`gpt-4o` などの「知っている有名なモデル名」に対してのみ、ツール呼び出し機能や高度なストリーミング処理を正常な形式でオンにする仕様（ハードコード）になっていると推測されます。

**【検証ステップ（新しい計画）】**
1. [x] **ステップ1：モデル名のエイリアス（gpt-4o化）のテスト**
   - `opencode.json` を編集し、プロバイダーを安定稼働した `@ai-sdk/openai-compatible` 形式（カスタム定義）に戻します。
   - その際、モデル名として明示的に `"gpt-4o"` をマッピングします。
   - サーバー側（LiteLLM）の `config.yaml` では既に `gpt-4o` としてリクエストを受け取り、`qwen` に流す設定が存在するため、これを利用してツール機能が解放されるか確認します。
   - **完了**: `opencode.json` を書き換えました。
   - **結果**: 失敗。LiteLLMサーバー側から `Invalid model name passed in model=gpt-4o.` というエラーが返却されました（APIキーの権限、もしくはサーバー側の設定未反映が原因）。
2. [ ] **ステップ2：ローカル専用プロバイダー定義のテスト（サーバー側の変更不要なアプローチ）**
   - ステップ1のサーバー側エラーを深追いせず（あっちこっち行かず）、計画通りステップ2へ進みます。
   - 公式ドキュメントにある「ローカル環境向けプロバイダー（`lmstudio` または `llama.cpp`）」を使用します。
   - これらは名前を `gpt-4o` に偽装しなくても、ローカルモデルとして正しく認識され、ストリーミングやツールが機能するようにOpenCode側で最適化されています。
   - `opencode.json` を `lmstudio` プロバイダーとして書き換え、再度テストをお願いします。
